Red LED Panel 8×2

Overview · Project overview and quick start · README.md

Version 1.6.0 — Wi-Fi setup, live local time, a ten-scene showcase with your own scrolling message, a faster refresh driver, and firmware upload over Wi-Fi.

An animated showcase for an ESP32 and a red 64×16 HUB08 panel: bouncing balls, a starfield, pixel rain, animated bars, Conway's Life, beating hearts, scrolling text, Pong, and a network-synchronised clock. Two simple patterns make it easy to check placement and pixel detail.

The panel is an 8×2 grid of 8×8 modules, with one colour driven through R1. Drawing uses Adafruit GFX; the driver continuously refreshes the display in the background.

Get started

  1. Connect the panel's 5 V supply, common ground, and eight control signals through a level shifter. Use the wiring table.
  2. Open this project in VS Code with PlatformIO. Build and upload:
pio run
pio run --target upload
pio device monitor --baud 115200

After the first USB upload, set SECRET_OTA_PASSWORD in include/secrets.h to upload over Wi-Fi with pio run -e esp32dev_ota --target upload; see Upload over Wi-Fi. 3. Three boot cards show the header, display settings, and network state, then the clock starts the cycle. Serial Monitor prints the full startup/settings report and each scene. 4. Type 1–9 or c (clock) to select a scene, n for next, p to pause/resume, or + / - to change brightness. No Enter is needed.

The default cycle is clock → checkerboard → clock → bouncing balls → clock → next demo, continuing through Pong and repeating. The clock stays for 10 seconds by default; change it on the settings page (5–3600 s). A full rotation takes about three minutes with the defaults. Selecting a demo runs it immediately, then returns to the clock before the following demo; use p to keep a scene on screen. f, o, and b provide all-off, all-on, and output blanking. r restarts at the clock, with the checkerboard next; ? prints help.

The scrolling message is set on the settings page (up to 64 plain characters). Left empty, it shows device details: firmware version, uptime, time since the last network sync, the panel's address and location. The message always scrolls fully off the panel before the clock returns.

Pong plays automatically; no controllers are required. c holds the live clock on screen; n leaves it and p resumes the playlist timer. Time continues while the playlist is paused.

Connect Wi-Fi and set your location

If a saved network is unavailable after 10 seconds, join RedPanel-XXXXXX using PanelSetup32 (change it in a gitignored include/secrets.h, copied from include/secrets.example.h), then open http://192.168.4.1/. Choose your 2.4 GHz Wi-Fi network and enter its password. Credentials are stored on the ESP32, not in the source.

After connection, open http://<panel-IP>/ using the address printed by serial; a sidebar moves between the clock, settings, connection and device sections and the Wi-Fi pages. Set the location, time zone, startup brightness, startup view, clock time between demos and scrolling message. Defaults are Sydney, Australia/Sydney, 90/255, Clock + demos, 10 s and device details. Daylight saving follows the selected zone automatically. An optional SECRET_PANEL_PASSWORD adds a login to the settings page.

The clock waits for an NTP response rather than displaying a sample time. After losing Wi-Fi it continues from its last sync for up to 24 hours, with the colons held solid instead of blinking. Send w to reopen setup, i for status, and d to cycle debug levels.

Display refresh uses hardware-timed blanking and a dedicated scan task, with complete-frame updates to reduce tearing. From v1.2.0 the next row is shifted over hardware SPI while the current row is lit, so the full brightness range is usable. The reference panel ran v1.2.0 with zero missed or late rows. Send i for refresh timing counters; see the flicker check after uploading. Clock colons blink and hearts pulse deliberately.

The reference ESP32/panel checks on 25 October 2026 (v1.1.0, then v1.2.0) confirmed Wi-Fi connection, NTP time and clock/demo progression. The user observed no visible flicker, with no increase in missed/late refresh counters between two held-letter readings.

The ESP32 reference test setup contains every connection, buffer pin, network address, default setting and bench check. Screen examples show rendered output for every demo and startup/clock state.

Make it yours

Set the scrolling message and clock time on the settings page. Change DEFAULT_BRIGHTNESS and animation timing in include/config.h. Scene lengths and drawing routines are in src/main.cpp. The panel guide includes the complete control reference, power and wiring details, and examples for drawing your own text and graphics.

The pin map, orientation and timing settings are in the panel guide. Monitor speed is 115200 baud.

Panel hardware and usage guide

Panel guide · Hardware, wiring, firmware, and daily use · docs/PANEL_GUIDE.md

Build a compact animated display with an ESP32, a 5 V HUB08 panel, and Adafruit GFX. This guide covers the working setup and the ten-scene showcase.

What the panel can do

This red P3.75, 64×16 panel contains sixteen 8×8 modules in an 8×2 grid. Every pixel is individually addressable, making it suitable for text, icons, simple games, cellular automata, and motion effects. Pixels are on/off; brightness control applies to the whole display rather than to individual pixels.

The driver scans one of sixteen rows at a time. Background refresh continues while your application draws or pauses. The configured 500 µs row period gives a nominal 125 Hz complete refresh; scene animation runs separately, typically at 25 frames per second.

Rear PCB: INPUT200 at left, OUTPUT201 at right, power near the centre. These reference photos come from the original bring-up board.

Power and level shifting

Use a regulated 5 V supply connected directly to the panel's VCC/GND screw terminal. A 2–3 A supply is a practical starting point, not a measured maximum panel rating. Keep power leads short and adequately sized. Join the panel, ESP32, and level-shifter grounds. Route LED-panel current through its power terminal rather than through the ESP32 or breadboard rails.

Start at the default brightness 90/255. Increasing brightness or the number of lit pixels increases the load. Since v1.2.0 the top of the brightness range is usable: full brightness lights each row for about 89% of its slot (previously about 50%), so peak current at 255/255 is roughly 1.8 times the v1.1.0 figure. Size the supply accordingly. USB can power the ESP32 while the separate supply powers the matrix; their grounds must be common.

Pass all eight control signals through a level shifter from ESP32 3.3 V logic to the panel's 5 V logic. The recorded setup uses an EzSBC LS1. Its VLo connects to 3.3 V, VHi to the panel logic supply, and each Lo channel pairs with the matching Hi channel. LS1 uses resistor pull-ups; a 74AHCT245 provides actively driven outputs and is another suitable interface. EzSBC LS1 description, manufacturer design notes

ESP32-to-matrix wiring

These are ESP32 GPIO numbers, not development-board header positions. Connect to INPUT200 beside U201.

ESP32 GPIO Matrix signal Config name Function
25 LA PIN_A Row-address A
26 LB PIN_B Row-address B
27 LC PIN_C Row-address C
13 LD PIN_D Row-address D
22 EN PIN_OE Output enable
23 R1 PIN_R1 Red pixel data
4 LT PIN_LAT Column latch
18 SK PIN_CLK Shift clock
GND GND — Common reference

All eight signals travel ESP32 → low-side input → matching high-side output → matrix input. R2/G1/G2 are unused by this firmware. The configured pins are below 32, as required by the driver's direct GPIO writes. R1 and SK are driven by the ESP32's VSPI hardware SPI peripheral at SHIFT_CLOCK_HZ (500 kHz), routed to GPIO 23/18 through the GPIO matrix.

Connector reference

The pictured board has an unmarked INPUT200 and labelled OUTPUT201. With the rear PCB text upright, OUTPUT201 reads as follows. Row numbers are descriptive, not official IDC pin numbers.

                    LEFT       RIGHT
Top, row 1          GND        LA
     row 2          GND        LB
     row 3          GND        LC
     row 4          EN         LD
     row 5          R1         G1
     row 6          R2         G2
     row 7          GND        LT
Bottom, row 8       GND        SK

The matching INPUT200 ground positions in left rows 1/2/3/7/8 were verified on this board. Use this as the connector orientation reference for this panel, not a universal pinout for every HUB08 product. OUTPUT201 is for cascading onward; this firmware controls one 64×16 panel.

Using a 74AHCT245

For a standard 20-pin 74AHCT245, connect pin 20/VCC and pin 1/DIR to 5 V, and pin 10 (GND) and pin 19 (/OE) to ground. Add a 100 nF decoupling capacitor close to VCC/GND. This selects A-to-B direction. Verify the exact package pinout used. The chip's buffer-enable pin is separate from matrix EN. The per-signal buffer pin table is in the ESP32 test configuration. Build and run

Open the project in VS Code with PlatformIO, select environment esp32dev, and use Build, Upload, then Serial Monitor. The project uses espressif32@6.9.0, Arduino, and Adafruit GFX. From the PlatformIO terminal:

pio run
pio device list
pio run --target upload
pio device monitor --baud 115200

Choose the USB port for your ESP32 if several devices are connected. Close an existing monitor before uploading. Reset the board with Serial Monitor open to see the startup message.

The display shows three startup cards, then enters the saved startup view: Clock + demos by default, or a held live clock. Serial prints each scene's number, name, and short description. There is no long blank interval between scenes.

Upload over Wi-Fi (OTA)

After one USB upload of v1.3.0 or later, new firmware can be sent over the local network, for example from a laptop while the panel stays connected elsewhere.

  1. Copy include/secrets.example.h to include/secrets.h (gitignored) and set SECRET_OTA_PASSWORD. An empty password disables network uploads.
  2. Upload once over USB with pio run --target upload. Serial then prints [ota] Ready: red-panel-xxxxxx.local port 3232 after Wi-Fi connects.
  3. On any computer on the same network, use the same include/secrets.h (it is not in git) and run:
pio run -e esp32dev_ota --target upload

The upload reads the password from include/secrets.h. When changing the OTA password, put the new one in secrets.h and give the panel's current one for that single upload: PANEL_OTA_PASSWORD='old-password' pio run -e esp32dev_ota --target upload.

The esp32dev_ota environment refuses to build without SECRET_OTA_PASSWORD, because that firmware would switch OTA off and need USB again. It targets this panel's mDNS name, red-panel-a4ae30.local. For another panel, change upload_port or add --upload-port <IP>. The default esp32dev partition table already has two 1.25 MB app slots, so no custom table is needed; firmware uses about 0.94 MB.

The panel shows OTA with a percentage and progress bar, then restarts on success. If an upload fails, the current firmware keeps running and the scene returns. Flash writes pause row scanning briefly, so the progress display can flicker. The upload needs the computer and panel on the same network; macOS may ask to allow incoming connections for Python, which espota uses for the transfer. From outside your home network, use a VPN into it rather than exposing port 3232.

Wi-Fi, location and startup status

The firmware includes WiFiManager 2.0.17, persistent panel settings, and NTP time. If it cannot connect using saved credentials within 10 seconds, it opens RedPanel-XXXXXX with setup password PanelSetup32 (the default from include/secrets.example.h; set your own in a gitignored include/secrets.h). Join it and open http://192.168.4.1/ to select a 2.4 GHz network.

Once connected, open http://red-panel-xxxxxx.local/ or the serial-reported IP address (/panel also works). A sidebar, like this documentation's, moves between Clock, Settings, Connection and Device, and links to the Wi-Fi network and system-info pages; those pages carry a bar back to the settings. The Device section shows firmware version and whether Wi-Fi upload (OTA) is ready. Set your location label, time zone, startup brightness, startup view, clock time between demos and scrolling message. Defaults are Sydney / Australia/Sydney, 90/255, Clock + demos, 10 s and an empty message (device details). The page also shows the device's time, network and hardware settings. Saving applies brightness at once and only restarts the display when the startup view changes. Set SECRET_PANEL_PASSWORD in include/secrets.h to require a login (user admin) for /panel and its API. w reopens setup and i prints status.

Boot prints the firmware header, GPIO map, timing, orientation, location/time zone and connection details. Three 2-second panel cards show version, geometry/brightness, then network/time state. Saved settings are loaded before displaying content at the configured brightness.

Use the complete ESP32 test configuration for exact buffer/header connections, provisioning, network services, persistence and acceptance checks. Generated examples show the expected output for all scenes and status states.

Clock → checkerboard → clock → balls → clock → stars, and so on through Pong, then repeat. The clock time between demos is set on the settings page (5–3600 s, default 10). A complete rotation is about three minutes with the defaults; the device-details message takes roughly 40 seconds to scroll, at 12 pixels per character and 25 steps per second.

Scrolling text shows the message saved on the settings page: up to 64 plain characters (space to ~), so the panel font can draw every one. Left empty, it shows device details composed when the scene starts, for example RED PANEL v1.6.0 - UP 2H 05M - SYNCED 3M 10S AGO - 192.168.1.163 - Sydney. The scene length is worked out from the message width, so the whole message always crosses the panel before the clock returns. A directly selected demo returns to the clock, then advances to the following demo. n follows the same clock/demo alternation. The bars are a simulated equalizer, not an audio measurement. Life is a real cellular-automaton update: a cell survives with two or three neighbours and is born with three. It starts from the same gliders and blinkers each time that scene is entered.

Hearts vary the whole-panel requested brightness from about one fifth of your selected level up to that level. The display is monochrome, so the star and rain trails use shapes and spacing rather than per-pixel grey levels.

Pong and live clock

Pong is a fully automatic match. Two paddles follow a two-pixel ball, which rebounds off the top, bottom, and paddles. Paddles sometimes miss after a rally so goals and new serves occur. Each score is a single digit that wraps after 9; selecting 9 starts a fresh match. Use p to freeze or resume play.

Clock displays real local time after synchronising with NTP. It uses the saved time zone for daylight saving. Before the first sync it shows NO WIFI / JOIN AP or SYNC TIME / WAIT NTP. The lower row shows the day and date in small capitals, for example SUN 25 OCT 2026. Colons light for the first half of each real second while Wi-Fi is connected; solid colons mean the clock is holding time offline from its last sync. Without a fresh sync for 24 hours (CLOCK_HOLDOVER_MAX_MS) the clock returns to its waiting display rather than showing drifted time. Selecting c holds the clock without resetting it; pausing the playlist leaves time running. No RTC module is required, but a fresh boot waits for network time.

Serial controls

Click inside the PlatformIO Serial Monitor terminal and type a key. No Enter or comma is required. Letter commands also accept uppercase. Local echo may be off; the firmware's printed response confirms receipt.

From held f/o/b, p, r, or n returns to the clock (r also resets the next demo to the checkerboard). Scene keys (1–9, c) also leave any held pattern. Changing brightness preserves the current frame and pause state; b remains blank even if you increase the selected level. The selected brightness persists between scenes. Five seconds after the last +/- (BRIGHTNESS_SAVE_DELAY_MS) it is saved as the startup brightness, so a burst of key presses writes flash once. Brightness zero remains dark until increased again.

Requested brightness is an on-time setting (level × 500 µs / 255), not a calibrated light percentage. The next row is shifted while the current row is lit, so only the latch and a 50 µs guard are dark; the on-time caps at about 445 µs, so roughly 228–255 look the same.

For a quick orientation check, send c and p: the clock digits and the day/date row should read left to right, top to bottom. o lights every pixel to find dead or stuck modules. (The letter test used during bring-up was removed in v1.6.0.)

Draw your own content

Hub08Panel derives from Adafruit_GFX. Colour 0 is OFF and a nonzero colour is ON. Draw text or graphics, then call show(). For a permanent label, replace the demo application in src/main.cpp with:

#include <Arduino.h>
#include "Hub08Panel.h"

Hub08Panel panel;

void setup() {
  Serial.begin(115200);
  panel.begin();
  panel.setBrightness(DEFAULT_BRIGHTNESS);
  panel.setTextWrap(false);
  panel.setTextSize(1);
  panel.setTextColor(1);
  panel.fillScreen(0);
  panel.setCursor(1, 0);
  panel.print("READY");
  panel.setCursor(1, 8);
  panel.print("ESP32");
  panel.show();
}

void loop() {
  delay(10);  // Background scanning keeps the label visible.
}

Use this instead of the original setup()/loop(), rather than adding a second pair. To draw a border, line, and circle after initialisation:

panel.fillScreen(0);
panel.drawRect(0, 0, PANEL_WIDTH, PANEL_HEIGHT, 1);
panel.drawLine(0, 0, PANEL_WIDTH - 1, PANEL_HEIGHT - 1, 1);
panel.drawCircle(32, 8, 5, 1);
panel.show();

Size-1 text fits two rows of small characters. Size-2 text gives a single 14-pixel-tall line, as used by the scroller. setTextWrap(false) lets text move through the screen edges. GFX clips drawing to the framebuffer and honours setRotation().

Driver API

Method Use
begin() Initialise pins and SPI, preload blank data, start background refresh; call once
drawPixel(x, y, colour) Set a pixel, with clipping and GFX rotation
fillScreen(colour) Clear or fill the drawing buffer
show() Queue the drawing buffer for the next complete scan
setBrightness(level) Set requested row on-time; zero blanks output
rowAddressFor(y) Return the mapped hardware address for a logical row
refreshStats() Snapshot cumulative rows/deadlines and maximum wake/scan times

The working, pending and active framebuffers each occupy 128 bytes. show() copies to the pending buffer; refresh applies it only when row zero of the next scan is prepared, so one complete scan uses one picture. Brightness changes as row zero is latched.

Hardware timer TG0/T0 sets the 500 µs row cadence and blanks output. A dedicated high-priority task on core 1 then sets the address and latches the columns that were shifted during the previous slot, lights the row, and shifts the following row's 64 bits over hardware SPI while this one is lit. The 74HC595 outputs only change on LT, so shifting does not disturb the lit row. TG0/T1 ends the brightness pulse in a short interrupt; the row interrupt supplies a second blanking deadline. Late rows remain dark and missed ticks are skipped. These two timers are reserved for the panel. Their IRAM handlers use shared interrupts at an available level 1–3, avoiding the two exclusive level-3 allocations that caused a blank display during startup. ESP-IDF interrupt allocation Interrupts do not shift data or print logs. This removes row work from the shared esp_timer task that Wi-Fi activity can delay. The pin map, polarity, 1 µs address/latch phases and nominal 125 Hz refresh are unchanged from v1.1.0. The v1.2.0 overlapped SPI shift was checked on the reference panel on 25 October 2026: normal display through 255/255, with zero missed ticks or late rows over more than 500,000 rows (recorded result). On another panel, if output ghosts or misplaces columns, try a lower SHIFT_CLOCK_HZ and report the i refresh counters. ESP-IDF hardware timer reference, ESP timer dispatch limitations

This addresses possible timing jitter and frame tearing. On 25 October 2026 the user confirmed no visible flicker on the reference panel; two held-letter readings showed increasing rows and unchanged missed/late counters. See the recorded v1.1.0 result for the measurements and scope. Flash writes can still pause the scan task briefly. See the bench flicker check; camera banding is a separate exposure effect.

Web settings and status

Browser preview using mock test-network data. The live page reads its status from your ESP32.

The page opens at / (or /panel). Its sidebar jumps between Clock, Settings, Connection and Device, and links to WiFiManager's Wi-Fi network and System info pages, which show a matching bar back to the settings. In the setup hotspot a Close setup hotspot link also appears. Under Settings, set:

  1. Location name: 1–32 UTF-8 bytes; defaults to Sydney.
  2. Time zone: choose a listed region. Australian zones, Auckland, UTC and several international zones are included.
  3. Startup brightness: 0–255; default 90. This is the requested on-time; roughly 228–255 look the same.
  4. Startup view: Clock + demos or Real-time clock. Clock + demos starts with the clock, runs one demo, returns to the clock, then runs the following demo.
  5. Clock time between demos: 5–3600 seconds; default 10. Applies from the next clock visit.
  6. Scrolling message: up to 64 plain characters (space to ~). Empty scrolls device details. The message always scrolls fully before the clock returns.

Choose Save and apply. The ESP32 validates the complete form, saves one record, and changes the local time zone and brightness at once. The display restarts only when the startup view changed. Settings survive reset. A failed flash write leaves the previous settings active. Serial +/- changes are saved as the startup brightness once, five seconds after the last key press.

The page shows the ESP32's time, location, date/zone, network name, signal, address, uptime, last sync age, firmware version, Wi-Fi upload (OTA) state and hardware settings. Its clock is read from the panel, not from the browser. Sync time requests another NTP update. Wi-Fi network opens WiFiManager's network form. Open setup hotspot, or serial w, opens provisioning again without erasing saved settings.

Status requests are read-only. Panel settings/sync/setup API mutations carry a boot-local token to prevent unrelated cross-origin pages from submitting changes. The page and APIs contain no Wi-Fi passwords; WiFiManager's internal debug output is disabled.

Live clock behaviour

Send c to keep the live clock on screen. p resumes the playlist's clock-scene timer; n moves to the next demo (the checkerboard immediately after a fresh boot/restart). With clock selected as the startup view, it remains visible after boot.

  • Before the first valid NTP response: NO WIFI / JOIN AP, or SYNC TIME / WAIT NTP.
  • After sync: local HH:MM:SS with colons lit for the first half of each second, and the day and date on the lower row, for example SUN 25 OCT 2026.
  • After losing Wi-Fi: time continues from the ESP32's last sync (holdover), with the colons held solid instead of blinking. Accuracy can drift until reconnection; after 24 hours without a sync the clock returns to the waiting display.
  • After reset or power loss: this firmware waits for a new network sync; it does not invent a sample time.
  • Pausing the playlist does not freeze the clock. Resuming or reselecting c does not reset the actual time.

The clock uses configTzTime() and localtime_r() with a region-specific daylight-saving rule. Espressif Arduino time implementation, WiFiManager 2.0.17

Blank screen with refresh setup error

If serial reports timer_isr_callback_add: register interrupt service failed, ESP_ERR_NOT_FOUND and Refresh: rows=0, the display scanner has not started. Application scene messages and Wi-Fi can still work while OE remains blanked. The earlier driver requested two exclusive level-3 interrupts; the corrected driver uses shared IRAM interrupts at an available level 1–3. This log identifies a firmware interrupt allocation failure.

Build/upload the corrected firmware and reset. Successful startup includes:

[INFO] HUB08 panel 64x16 started, row period 500 us (125 Hz frame)
[INFO] Refresh: hardware timers TG0/T0+T1, shared IRAM interrupts, scan task on core 1
[INFO] Shift: VSPI 500000 Hz on SK=18 R1=23, overlapped with the lit row

Send o (all on), then i twice a few seconds apart. The row count should be nonzero and increasing. A remaining setup error names the failed stage (for example, row interrupt); capture that line. Host tests model constrained allocation and startup cleanup. The reference-panel check below confirms that the corrected firmware started refresh and displayed successfully.

Check display flicker

Upload the new firmware, reset, and keep Serial Monitor at 115200 baud. Use r to verify clock → checkerboard → clock → bouncing balls, then further demos. A saved Real-time clock startup view stays on the clock; choose Clock + demos on the settings page to make the alternating cycle the boot default.

For a steady reference send c then p (held clock), then i. Observe the whole display by eye for 30 seconds; reload /panel several times, then send i again. Repeat with o (all on) at the normal 90/255 brightness. The status line includes:

Refresh: rows=..., missed ticks=..., late rows=..., max wake=... us, max scan=... us

Counters are cumulative since reset. Compare the two readings: missed ticks and late rows should stay unchanged during steady operation and normal page polling. Increasing values indicate missed refresh deadlines; record both reports and which action triggers them. Max wake/scan values are lifetime peaks, including startup or earlier flash saves, so reset for a fresh comparison. Saving settings or Wi-Fi credentials writes flash and can cause a brief disturbance; check that steady output resumes afterwards.

The driver isolates refresh from the shared timer task and commits pictures between scans. The v1.2.0 overlapped SPI shift passed this check on the reference panel (below). Host tests verify these decisions, but do not measure real interrupt latency or prove the LEDs are flicker-free. Clock colons light for half of each second and hearts change brightness intentionally. Camera bands can persist at 125 Hz even with a steady appearance by eye; see the photography guidance.

Maintainer notes · Architecture, constraints, and evidence limits · CLAUDE.md

Target

  • ESP32 DevKit (esp32dev), espressif32@6.9.0 = Arduino core 2.0.17 / IDF 4.4. Keep pinned: the driver uses legacy driver/timer.h (no gptimer before IDF 5).
  • Red HUB08 64×16 (8×2 modules), 1/16 scan, Adafruit GFX, WiFiManager 2.0.17. Firmware v1.6.0.
  • GPIO 25/26/27/13 → LA/LB/LC/LD, 22 → EN, 4 → LT direct register writes (all GPIO must be < 32). 23 → R1 and 18 → SK are VSPI (SPI HAL spiWriteNL, MSB first).
  • Active-low data and OE; reversed column stream (bit-reversed bytes in software), row bits {0,1,2,3}, row XOR 0x0F.

Refresh driver rules

  • TG0/T0 (row tick) and TG0/T1 (OE off) are reserved. Allocate both with ESP_INTR_FLAG_SHARED | ESP_INTR_FLAG_LOWMED | ESP_INTR_FLAG_IRAM; two exclusive level-3 requests failed with ESP_ERR_NOT_FOUND and left the panel blank.
  • ISRs only blank OE / notify; no logging, shifting or allocation. Row work runs in a high-priority task on the setup core, never in esp_timer.
  • Per tick: blank → address → latch the columns shifted in the previous slot → arm OE-off → shift the next row while lit. Frames commit only when row 0 is prepared; brightness when row 0 latches.
  • Late ticks leave the row dark; skip backlogs. Keep 500 µs row, 1 µs latch phases, 50 µs guard. Unwind timers, interrupts, SPI and task on any init failure.
  • v1.2.0 (overlapped 500 kHz SPI shift) confirmed on the reference panel 25 Oct 2026: 0 missed/late rows, peak wake 237 µs. v1.1.0 shifted while dark.

Application rules

  • Pong state changes only in stepPong(). Clock never invents an epoch; holdover ends 24 h after last sync. Clock visits end by elapsed time, not frames.
  • Unsigned millis() subtraction everywhere; render one frame, never replay missed frames. Log transitions, not frames.
  • Web settings save applies brightness live; the view restarts only if startClock changed. Serial brightness saves after a 5 s quiet period.

Network and storage

  • NVS namespace redpanel, key clock: one ClockSettings record (schema 2, adds clock hold and scroll text). A schema-1 record (by size) is upgraded on load with upgradeClockSettings(); any layout change needs a new schema and upgrade path. Validate before use; a failed write must not change active settings. NVS writes can stall the scan task briefly.
  • Register custom routes in WiFiManager's web-server callback so they survive portal/LAN switches; it runs before WiFiManager adds its own, so our / wins. WiFiManager pages get CSS and a nav bar through setCustomHeadElement. POSTs need the boot-local token.
  • secrets.h (gitignored) supplies SECRET_AP_PASSWORD, optional SECRET_PANEL_PASSWORD and SECRET_OTA_PASSWORD (empty = OTA off); secrets.example.h is the fallback. Never log credentials.
  • ArduinoOTA starts on first Wi-Fi connect with its own mDNS disabled; loop() owns mDNS and re-adds the arduino service on reconnect. ArduinoOTA.handle() blocks during an upload, so progress drawing runs from its callbacks. default_envs = esp32dev keeps plain uploads on USB.
  • include/ConfigPage.h is generated from web/index.html by tools/embed_web.py (pre-build hook). Edit the HTML, not the header.

Checks and docs

  • tools/render_examples.py runs host regressions (app, network, driver fixtures) and regenerates GIFs and docs/SCREEN_EXAMPLES.md. Not a hardware test.
  • tools/build_docs.py builds the single index.html (all Markdown, CSS inlined, release log from CHANGELOG and git) and the share ZIP. Never add per-document HTML.

Archived bring-up report

Archived bring-up · Historical investigation and panel replacement · docs/BRING_UP_REPORT.md

Historical reference: this report describes the diagnostic firmware used before the showcase. Its eleven tests and e/l/pre-scroll commands are retired. For current setup and controls, use the panel guide.

Project: Red LED Panel 8×2 · Recorded outcome: 24 October 2026 · Controller: ESP32 DevKit · Display: single-colour red P3.75 HUB08, 64×16 pixels.

Resolution

The original panel was faulty. After the owner replaced it with another panel described as exactly the same, the display worked with the existing setup. This was the decisive functional comparison.

The investigation also found crossed GPIO 26/27 row-address wiring, which was corrected separately. A software B/C exchange introduced during diagnosis was removed after that correction. Adding an EzSBC LS1 removed the observed flickering, but it did not remove the stuck section on the original panel.

The exact defective trace, latch connection, shift register, buffer, or output stage inside the original panel was not established. A measured OL between U105 and U107 latch pins remains an observation, not a proven root cause. The proposed comparison measurements on other adjacent chips were not reported before the successful panel replacement.

The starting point

The initial application already provided all-on, all-off, row-walk, and column-walk tests followed by scrolling text. Individual row/column logs used a verbose debug level, making it harder to compare the panel with serial output at the default settings.

The application was expanded into an eleven-test sequence with explicit descriptions and per-step serial output at 115200 baud. Controls were added to restart, pause, advance, and hold diagnostic states without stopping row refresh. Subsequent additions made a static letter pattern, the pre-scroll black state, runtime OE polarity, and LT-pulse width directly comparable.

The rightmost three module columns by two module rows stayed lit during tests. This is a 24×16-pixel section, or 384 LEDs; the responding left section covered five module columns. The physical left/right distinction later mattered when inspecting the board from behind.

Investigation chronology

1. Localised constant illumination and flicker

The owner reported that tests partially worked while the right 3×2 modules remained on. Later clarification established that the visible flickering was confined to that section rather than the whole panel.

The driver's column transmission covers all 64 bits on every row scan, including during a black frame. A different column orientation can rearrange content, but cannot turn a uniform black buffer into a solid lit block. A simple increase in shift-chain length was therefore not adopted as a fix: an intact continuously clocked chain would eventually fill with uniform OFF data.

2. Separate black data from output blanking

The held serial commands made the distinction observable:

Command Requested state Original-panel observation
f Black data, ordinary output timing Right 3×2 stayed on, steadily
o All pixels ON Entire panel on, no flicker in the held state
b All-one data with brightness 0 / OE disabled Entire panel dark

An early description that the section cleared “after Test 11” was ambiguous. Later the owner identified the exact line: brightness 0/255 (dark) in Test 11. That phase suppresses output through EN/OE. It does not show that the right section accepted black column data.

3. Explicit signal and refresh timing

The driver gained 1 µs data setup and clock high/low timing, plus latch settling intervals. Refresh was adjusted to blank before shifting, cancel old OE-off events, cap each light pulse to the remaining row time with a 50 µs margin, and skip overdue row callbacks rather than process a backlog in a burst.

These changes addressed identifiable timing weaknesses in the software. They were not evidence of a repaired panel, and they did not eliminate the original section fault.

4. Compare both black-frame entry paths

The pre-scroll interval and f both request a zero-filled 128-byte framebuffer at brightness 90/255. The s command was added to hold the exact pre-scroll state, while BLACK CHECK logged its settings.

The owner confirmed that f and s behaved the same, with the right section remaining on. This resolved the apparent difference between black-data states. The pre-scroll black interval was also lengthened to three seconds for easy observation.

A representative command report was:

TEST 2/11: ALL OFF - every LED should be dark
BLACK CHECK: frame=128 zero bytes, brightness=90/255,
             OE_ACTIVE_LOW=true, DATA_ACTIVE_LOW=true
R1 GPIO 23 should stay HIGH; each row still gets 64 SK clocks and one LT pulse.
HELD: pattern continuously shifted and latched at normal brightness

Serial labels describe intended electrical/display states; there is no automatic readback or wiring-fault detector in the firmware.

5. Add a level shifter

The initial ESP32-to-panel connection was direct. After a level shifter was fitted, the owner reported no flickering, while the right section still failed to clear with black data.

The specific device was subsequently identified as EzSBC.COM LS1. Earlier references to a possible HCT/AHCT buffer were therefore corrected in the documentation. LS1 uses a different design from the 74AHCT245 alternative described in the usage guide.

The flicker improvement was a real observation. It did not establish the cause of the remaining fixed section fault. The later successful identical-panel replacement is stronger evidence for that remaining fault being in the original panel.

6. Static letters reveal a second, independent mapping issue

The t mode displays one character per module:

A B C D E F G H
I J K L M N O P

The first photo showed letter-like content on the left, but in reversed order with displaced row strokes. The right section was fully lit. Comparing the glyph patterns with the installed GFX font suggested reversed columns, inverted row orientation, and an exchange of row bits B/C.

First static-letter photograph. The responding section has incorrect mapping; the right section remains solidly on.

Configurable output mapping was introduced. A follow-up photo showed ABCDE above IJKLM on the responding left five columns, while the right three columns remained on.

Second static-letter photograph, taken before the wiring-error correction was completed. It shows successful placement on the left, not a working replacement panel.

7. Find and correct crossed GPIO 26/27

The owner asked whether software was compensating for incorrect wiring. It could: a B/C permutation in code can hide crossed B/C wires.

The connections were traced and GPIO 26 and 27 were found to be wrong. The intended wiring is 26 → LB and 27 → LC through the level shifter. The wiring was corrected, and ROW_ADDRESS_Y_BITS was restored to {0, 1, 2, 3}. Column reversal and full row-address inversion were retained as viewing-orientation settings.

This was a separate fault from the right section remaining lit. Reordering rows or columns leaves a uniform zero buffer unchanged, so a mapping correction could not resolve that symptom.

8. Verify accessible voltages and header orientation

R1 voltage was measured while f and o held their states indefinitely. The input levels matched the requested active-low column-data convention. Supply values and later output-header readings were also recorded in the table below.

INPUT200 has no signal labels in the supplied image. OUTPUT201 does. The initial assumption of matching connector layout was treated as a hypothesis and the ground contacts were verified with all power disconnected. The owner confirmed continuity from the panel GND terminal to the proposed INPUT200 left contacts in rows 1, 2, 3, 7, and 8.

That confirms the ground pattern/orientation check, not a complete independent schematic trace of every connector signal. The subsequent replacement-panel result confirms the corrected setup was practically usable.

9. Test a longer latch pulse

The l comparison changes only LT high time, between the normal 1 µs and a 20 µs diagnostic setting, while holding the current image. It leaves the requested brightness, column data, and row mapping unchanged; row-time limits still apply.

The owner reported no change. Therefore a wider LT pulse by itself did not solve the original fault. This does not establish that every local latch/clock connection was intact, and no oscilloscope captures were supplied.

10. Inspect the physical boundary

The full rear view established that front-right corresponds to rear-left. The suspect area is around U101/U103/U105, with the working/stuck transition near U105/U107.

A close-up identified the SM74HC595D packages and the pin-1 orientation. Pin 12 is the storage/latch clock. With all power disconnected, resistance between U105 pin 12 and U107 pin 12 was reported as OL.

U105 at left and U107 at right. The image made package orientation readable for the resistance check. It does not establish an electrical break by itself.

Comparison checks were proposed between U103/U105 and U107/U109 latch pins. No results for those comparisons were recorded. No jumper repair, trace repair, chip replacement, or reflow outcome was reported.

11. Replace the panel

The owner obtained another panel described as exactly the same and replaced the original. The replacement worked. The reported change was the panel replacement; the fault investigation did not proceed to a component-level repair of the original.

The correct final diagnosis is therefore a faulty original panel, alongside a corrected external B/C wiring error and observed flicker improvement after adding level shifting. It is not a confirmed diagnosis of “U105 failed” or “the U105–U107 latch trace is broken.”

Lessons for the next panel

  1. Compare a known-good panel early when a sharply bounded section remains faulty after basic input checks. The replacement was the decisive experiment here.
  2. Verify wires before changing bit mappings. The temporary B/C compensation produced readable letters while hiding an external wiring error.
  3. Distinguish pixel OFF from OE blanking. A section going dark only at brightness 0 does not show that it accepted black data.
  4. Use a held, recognisable pattern. The sixteen static letters exposed mapping errors that moving text made difficult to interpret.
  5. Treat electrical measurements as bounded evidence. Correct DC levels do not replace pulse measurements; one open-circuit reading does not identify a failed chip.
  6. Keep observations separate from hypotheses. The record supports board replacement as the resolution without inventing a component-level cause.
